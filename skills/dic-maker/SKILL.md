# 개념사전 늘리기 (dic-maker)

`/study-notes`가 노트 주제를 고르는 개념사전(`catalog/items/*.json`)을 늘리는 스킬이다. **사전 저장소(`claude-study-notes`를 받은 폴더) 안에서 실행**해야 한다. 노트를 쓰지 않고 사전만 바꾼다. 사람이 승인하기 전에는 사전 파일을 건드리지 않는다. 예외는 사용자가 `auto`를 붙여 연 캠페인뿐이다("캠페인 (auto)").

## 0. 호출 인자를 먼저 해석한다

| 인자 | 할 일 |
|---|---|
| (없음) | 가장 비어 있는 단계에서 30개 → "절차" |
| `<단계> [개수]` (예: `4`, `4 30`, `2 20`) | 그 단계에서 그 개수(기본 30, 최대 60) → "절차". 60을 넘는 개수는 `auto`가 없으면 60으로 줄이고 "60을 넘기려면 `/dic-maker <단계> <개수> auto`로 캠페인을 여세요"라고 한 줄 알린다 |
| `<단계> <개수> auto` (예: `3 240 auto`, `3 1000 auto`) | 그 단계에 그 개수(최대 1000)를 60개 회차로 나눠, 회차마다 검토·자동 적용·커밋을 사람 승인 없이 이어 한다 → "캠페인 (auto)" |
| `a [개수]`, `all [개수]` (예: `a`, `a 30`) | 다섯 단계 모두 단계마다 그 개수(기본 30, 최대 60). 단계마다 에이전트 하나가 동시에 → "전체 단계 (a)" |
| `box` | study-notes 후보함(`~/StudyNotes/concept_candidates.md`)에 있는 개념만 사전에 넣는다 → "절차" (단계는 에이전트가 정한다) |
| `c`, `continue` | 진행 중인 실행을 초안이 있는 데서부터 이어 한다 → "절차" 3번부터 (`all` 실행이면 "전체 단계 (a)"의, 캠페인이면 "캠페인 (auto)"의 이어 하기) |
| `apply` | 사람이 승인한 초안을 사전에 넣는다 → "적용 (apply)" |
| `refresh` | 빨리 바뀌는 항목과 죽은 링크를 다시 확인한다 → "갱신 (refresh)" |
| `d`, `status` | 현황과 진행 중인 실행·캠페인을 보여 주고 끝 |
| `s`, `cancel` | 진행 중인 실행과 초안을 버리고 끝. 캠페인도 닫는다. 사전은 그대로다(이미 커밋된 회차 포함) |
| `h`, `help`, `?` | 아래 사용법을 그대로 출력하고 끝 |
| 그 외 | `알 수 없는 옵션입니다: <인자>` 한 줄 뒤에 사용법을 출력하고 끝 |

### 사용법 (h)
```
dic-maker — study-notes의 개념사전을 단계·분야별로 늘리는 스킬 (사전 저장소 안에서 실행)

사용법
  /dic-maker              가장 비어 있는 단계에서 주제·용어 30개 제안 → 검사 → 검토 → 승인 대기
  /dic-maker 4 30         4단계에서 30개 (단계 1~5, 개수 최대 60)
  /dic-maker 3 240 auto   3단계에 240개를 60개씩 4회차로. 회차마다 검토 → 자동 적용 → 커밋 (사람 승인 없음, 최대 1000)
  /dic-maker a 30         다섯 단계 모두 단계마다 30개 (에이전트 5개 동시, 단계별 검토표 5개, apply는 한 번)
  /dic-maker box          study-notes 후보함의 개념만 사전에 넣기
  /dic-maker c            끊긴 실행이나 캠페인 이어 하기
  /dic-maker apply        검토표를 보고 승인한 뒤 사전에 넣기 (버전 올림·커밋)
  /dic-maker refresh      빨리 바뀌는 항목과 죽은 링크 다시 확인
  /dic-maker d            현황 보기   /dic-maker s  실행 취소   /dic-maker h  이 사용법

메모
  · 주제와 용어를 그 단계의 목표 비율(대략 1:2)로 함께 늘린다. 30개면 주제 10개 + 용어 20개쯤이다
  · 항목은 공식 문서·표준·공신력 있는 기관 자료에서만 고르고, 자료 내용은 옮기지 않는다
  · 사람이 승인하기 전에는 사전 파일을 바꾸지 않는다. 승인 후 apply가 버전을 올리고 커밋한다
  · a는 150개(30×5)를 한 번에 제안한다. 20~40분, 첫 실측 기준 15~20달러쯤 든다
  · auto 캠페인은 사람 대신 검토 에이전트의 판정으로 넣는다. 자료를 확인하지 못했거나 판정이 없는 항목은 뺀다.
    회차마다 커밋되고 .dic-maker/campaign/에 검토표가 남는다. 60개 회차는 10~15분, 6~8달러쯤 든다 (240개 ≈ 1시간, 1000개 ≈ 4~5시간)
```

## 준비

- `$PY` = `python3 -I` (Windows는 `python -I`). 값을 명령에 그대로 쓴다.
- `$SKILL_DIR` = 이 SKILL.md가 있는 폴더. 플러그인이면 `${CLAUDE_PLUGIN_ROOT}/skills/dic-maker`, 직접 복사면 `$HOME/.claude/skills/dic-maker`.
- `$DM` = `$PY "$SKILL_DIR/scripts/dic_maker.py"`. 아래에서 `$DM`은 이 전체를 뜻한다. 변수에 담지 말고 명령마다 풀어 쓴다.
- 현재 폴더에 `catalog/tools/catalog.py`가 없으면 스크립트가 멈춘다. 그때는 "사전 저장소(claude-study-notes) 폴더에서 다시 불러 주세요"라고 알리고 끝낸다. 다른 폴더에서 `--repo`로 가리켜도 되지만 커밋은 그 저장소에서 한다.
- 에이전트를 띄울 수 없는 환경(Codex 등)에서는 같은 일을 순서대로 직접 한다.

스크립트 출력은 `head`로 자르지 않는다. 비용이나 사용 한도를 짐작해 개수나 분량을 줄이지 않는다. 한도 오류가 실제로 났을 때만 멈추고 그대로 알린다.

## 절차

1. **계획**
   ```bash
   $DM start [--level <단계>] [--count <개수>] [--box]
   ```
   진행 중인 실행이 있다고 멈추면 `/dic-maker c`나 `/dic-maker s`를 안내하고 끝낸다. 출력에서 쓰는 값: `level`, `topics`·`terms`(주제·용어 몫), `quotas`(분야별 몫), `draft_files`(분야별 초안 파일 경로), `domains`(분야 이름과 기준 자료), `ladder_gaps`(심화만 있고 입문이 없는 묶음), `box`(사전에 없는 후보함 개념), `agent_concurrency`.
   한 줄로 알린다: "📚 dic-maker · <level>단계 · 주제 <topics>개 + 용어 <terms>개 · 분야 <quotas의 키들> · 취소 ESC 후 /dic-maker s". 기다리지 않고 진행한다.

2. **분야마다 조사 에이전트 하나**를 띄운다. `agent_concurrency`(5개)까지 동시에. 모델은 지정하지 않는다. 지시문은 아래를 그대로 전하고 줄이지 않는다. `<...>`만 채운다.
   ```
   당신은 기술 교재의 편집자입니다. 개념사전에 넣을 항목을 공식 자료를 근거로 제안합니다. 대화를 알 필요가 없습니다.
   - 먼저 읽을 것: <DM> guide --domain <분야> --level <단계> 의 출력 전부 (규칙, 단계 기준, 항목 형식, 이 분야의 기존 항목, 넓은 말). SKILL.md를 따로 읽지 않습니다. 명령 사이에 echo ====를 넣지 않습니다.
   - 할 일: <분야>(<분야 이름>) 분야, <단계>단계에 주제 <n>개와 용어 <m>개를 제안합니다. 후보함 개념 <box 중 이 분야에 맞는 것>이 있으면 먼저 넣습니다. 사다리 빈칸 <ladder_gaps 중 이 분야>이 있으면 그 묶음의 입문 주제를 우선합니다.
   - 방법: 기준 자료 <domains[분야].sources>의 목차와 그 분야의 다른 공식 문서(언어·프레임워크·표준·공신력 있는 기관)를 WebFetch로 읽고, 그 단계의 includes에 맞고 excludes에 걸리지 않는 주제를 고릅니다. 항목마다 그 페이지를 refs에 넣고 basis에 근거를 적습니다. 자료의 문장은 옮기지 않습니다. 블로그·강의·roadmap.sh는 쓰지 않습니다. 기억만으로 쓰지 않습니다.
   - 용어는 이번 주제나 기존 주제가 가르치는 것이면 parent를 쓰고, 딸릴 주제가 없으면 parent 없이 refs를 넣습니다.
   - 쓸 파일: <draft_file>. JSON 배열 하나. 각 항목은 사전 항목 형식에 basis 칸을 더한 것입니다. 억지로 개수를 채우지 않습니다. 좋은 항목이 모자라면 모자란 대로 씁니다.
   - 다 쓰면 검사합니다: <DM> check --links
     이 분야 id가 들어간 오류를 모두 고칩니다. 다른 분야의 오류와 quota.short는 무시합니다. 경고는 읽고 판단해 고칠 것만 고칩니다. 검사를 피하려고 항목을 지우지 않습니다. 정말 겹치는 항목이면 지우고 basis 대신 마지막 응답에 그 이유를 적습니다.
   - 명령 하나가 권한 거부로 막혀도 Bash 전체가 막힌 것이 아닙니다. 더 단순한 명령이나 다른 도구로 계속합니다. git을 쓰지 않고 다른 스킬을 부르지 않습니다. 사전 파일(catalog/items)은 고치지 않습니다.
   - 마지막 응답은 세 줄입니다. 첫 줄 "완료 <분야>: 주제 n개, 용어 m개" 또는 "실패 <분야>: 이유", 둘째 줄 열어 보지 못한 자료(없으면 "없음"), 셋째 줄 기존 항목을 고치자는 제안(없으면 "없음").
   ```
   `box` 모드에서는 분야 대신 후보함 개념 목록을 주고 `--domain`을 빼며, 에이전트가 분야와 단계를 정해 `box.json` 하나에 쓴다.
   에이전트가 실패해도 멈추지 않는다. 사용자에게 묻지 말고 나머지를 계속하고, 끝나면 실패한 분야만 한 번 더 띄운다.

3. **전체 검사**
   ```bash
   $DM check --links
   ```
   `errors`가 남으면 그 분야의 에이전트에게 오류 목록을 주어 고치게 한다(같은 에이전트에게 이어서 보내도 되고 새로 띄워도 된다). 최대 3번 반복한다. 그래도 남는 오류가 있는 항목은 초안에서 빼고 보고에 적는다. `quota.short`는 오류가 아니다.

4. **독립 검토 에이전트** 하나를 띄운다. 모델은 지정하지 않는다.
   ```
   당신은 개념사전의 적대적 검토자입니다. 제안자의 말을 믿지 말고 자료로 확인합니다.
   - 읽을 것: <DM> guide --level <단계> 의 출력, 초안 파일 <draft_files 전부>, 기존 사전 <저장소>/catalog/dist/<단계>단계_*.md
   - 항목마다 확인: (1) refs를 WebFetch로 열어 summary·objectives가 그 자료와 맞는가, 사실 오류는 없는가 (2) 단계가 levels의 includes·excludes에 맞는가, 더 쉬운 단계나 어려운 단계가 아닌가 (3) 기존 항목이나 다른 초안과 내용이 겹치지 않는가 (4) 별칭이 다른 뜻으로도 흔히 쓰이지 않는가 (5) 중요도가 그 단계의 학습자에게 맞는가 (6) 선수 개념이 거꾸로이거나 빠지지 않았는가.
   - 결과는 <저장소>/.dic-maker/review-findings.md 에 씁니다. 항목 id마다 "유지" 또는 "수정: <무엇을 어떻게>" 또는 "삭제: <이유>"를 한 줄로, 자료를 확인한 것은 확인했다고 적습니다. 확인하지 못한 자료도 적습니다.
   - 초안 파일과 사전 파일은 고치지 않습니다. git을 쓰지 않습니다.
   - 마지막 응답은 두 줄입니다. 첫 줄 "검토 완료: 유지 n, 수정 m, 삭제 k", 둘째 줄 확인하지 못한 것(없으면 "없음").
   ```
   검토 결과를 초안에 반영한다(수정·삭제). 반영한 항목이 있으면 3번 검사를 다시 하고, **바뀐 항목만** 같은 검토 에이전트에게 한 번 더 보낸다. 두 번째 검토의 지적은 반영하되 세 번째 검토는 하지 않는다.

5. **검토표를 만들고 멈춘다**
   ```bash
   $DM review-sheet
   ```
   출력의 `review` 경로를 알리고, 단계·항목 수(주제·용어)·분야별 수·검사 오류·경고 수·검토에서 고친 수·삭제한 수·열어 보지 못한 자료를 5~8줄로 보고한다. 마지막 줄: "검토표를 보고 승인하시면 `/dic-maker apply`로 사전에 넣습니다. 빼고 싶은 항목은 말씀해 주시거나 초안 파일에서 지우세요." **여기서 끝낸다. apply를 스스로 실행하지 않는다.**

## 전체 단계 (a)

다섯 단계를 한꺼번에 늘린다. **단계마다 조사 에이전트 하나**가 자기 단계의 분야를 모두 맡고, 다섯이 동시에 돈다. 에이전트끼리 같은 파일을 쓰지 않도록 초안은 `draft/L<단계>/<분야>.json`에 나뉘고, 공유 파일(링크 캐시·대화 기록 색인)은 스크립트가 잠금과 임시 파일 교체로 지킨다. 에이전트는 자기 단계 폴더 밖의 파일을 만들거나 고치지 않는다.

1. **계획**
   ```bash
   $DM start --all [--count <개수>]
   ```
   진행 중인 실행이 있다고 멈추면 `/dic-maker c`나 `/dic-maker s`를 안내하고 끝낸다. 출력의 `plans`에 단계마다 `topics`·`terms`·`quotas`·`draft_files`·`level_info`·`ladder_gaps`·`domains`가 있고, `box`·`agent_concurrency`·`alias_sessions`는 공통이다. 별칭 대조용 대화 기록 색인은 여기서 미리 만들어진다.
   한 줄로 알린다: "📚 dic-maker · 다섯 단계 · 단계마다 주제 <topics>개 + 용어 <terms>개 · 에이전트 5개 동시 · 취소 ESC 후 /dic-maker s". 기다리지 않고 진행한다.

2. **단계마다 조사 에이전트 하나**, 다섯을 동시에 띄운다. 모델은 지정하지 않는다. 지시문은 아래를 그대로 전하고 줄이지 않는다. `<...>`만 그 단계의 `plans[단계]` 값으로 채운다.
   ```
   당신은 기술 교재의 편집자입니다. 개념사전의 <단계>단계에 넣을 항목을 공식 자료를 근거로 제안합니다. 대화를 알 필요가 없습니다.
   - 먼저 읽을 것: <DM> guide --level <단계> --domain <분야1> --domain <분야2> ... 의 출력 전부 (규칙, 단계 기준, 항목 형식, 분야마다의 기존 항목, 넓은 말). SKILL.md를 따로 읽지 않습니다. 명령 사이에 echo ====를 넣지 않습니다.
   - 할 일: <단계>단계에 분야별로 <quotas: 분야마다 주제 n개·용어 m개>를 제안합니다. 후보함 개념 <box 중 이 단계에 맞을 만한 것>이 있으면 먼저 넣습니다. 사다리 빈칸 <ladder_gaps>이 있으면 그 묶음의 입문 주제를 우선합니다.
   - 방법: 분야마다 기준 자료 <domains[분야].sources>의 목차와 그 분야의 다른 공식 문서(언어·프레임워크·표준·공신력 있는 기관)를 WebFetch로 읽고, 이 단계의 includes에 맞고 excludes에 걸리지 않는 주제를 고릅니다. 항목마다 그 페이지를 refs에 넣고 basis에 근거를 적습니다. 자료의 문장은 옮기지 않습니다. 블로그·강의·roadmap.sh는 쓰지 않습니다. 기억만으로 쓰지 않습니다.
   - 용어는 이번 주제나 기존 주제가 가르치는 것이면 parent를 쓰고, 딸릴 주제가 없으면 parent 없이 refs를 넣습니다.
   - 쓸 파일: 분야마다 <draft_files[분야]> 하나씩, JSON 배열. 각 항목은 사전 항목 형식에 basis 칸을 더한 것이고 level은 모두 <단계>입니다. 분야 하나를 다 쓰면 그 파일을 저장하고 다음 분야로 갑니다. 이 폴더(<draft/L단계>) 밖에는 아무 파일도 만들거나 고치지 않습니다. 이미 있는 파일은 지난 실행이 쓴 것이니 읽고 모자란 분야만 씁니다. 억지로 개수를 채우지 않습니다. 좋은 항목이 모자라면 모자란 대로 씁니다.
   - 다 쓰면 검사합니다: <DM> check --links --level <단계>
     이 단계 항목이 들어간 오류를 모두 고칩니다. quota.short는 무시합니다. "[단계 간]"이 붙은 오류는 다른 단계 에이전트가 같은 개념을 낸 것입니다. 고치지 말고 그대로 두고 마지막 응답에 적습니다. 어느 단계에 둘지는 검토 단계가 정합니다. "쓰는 중이라 건너뛴다"는 경고는 다른 단계 파일이니 무시합니다. 그 밖의 경고는 읽고 판단해 고칠 것만 고칩니다. 검사를 피하려고 항목을 지우지 않습니다. 정말 겹치는 항목이면 지우고 마지막 응답에 그 이유를 적습니다.
   - 명령 하나가 권한 거부로 막혀도 Bash 전체가 막힌 것이 아닙니다. 더 단순한 명령이나 다른 도구로 계속합니다. git을 쓰지 않고 다른 스킬을 부르지 않습니다. 사전 파일(catalog/items)은 고치지 않습니다.
   - 마지막 응답은 네 줄입니다. 첫 줄 "완료 <단계>단계: 주제 n개, 용어 m개 (분야별 …)" 또는 "실패 <단계>단계: 이유", 둘째 줄 열어 보지 못한 자료(없으면 "없음"), 셋째 줄 [단계 간] 겹침(없으면 "없음"), 넷째 줄 기존 항목을 고치자는 제안(없으면 "없음").
   ```
   에이전트가 실패해도 멈추지 않는다. 사용자에게 묻지 말고 나머지를 기다리고, 끝나면 실패한 단계만 한 번 더 띄운다. 그 단계 폴더에 이미 쓰인 분야 파일은 두 번째 에이전트가 읽고 이어 쓴다.

3. **전체 검사**
   ```bash
   $DM check --links
   ```
   `--level` 없이 돌리면 다섯 단계의 초안을 한꺼번에 보고 단계 사이 겹침(`cross_level`)도 나온다. `[단계 간]`이 아닌 오류가 남으면 그 단계의 에이전트에게 오류 목록을 주어 고치게 한다. 최대 3번 반복한다. 그래도 남는 오류가 있는 항목은 초안에서 빼고 보고에 적는다. `quota.short`는 오류가 아니다. `[단계 간]` 오류는 4번의 검토가 정한다.

4. **단계마다 독립 검토 에이전트 하나**, 다섯을 동시에 띄운다. 지시문은 "절차" 4번의 적대적 검토자 지시문에서 `초안 파일`을 그 단계의 `draft_files` 전부로, 결과 파일을 `.dic-maker/review-findings_<단계>.md`로 바꾸고, 아래 한 줄을 덧붙인다.
   ```
   - 단계 사이 겹침: <check 출력의 cross_level 중 이 단계 id가 든 것>. 상대 단계의 그 항목도 읽고, can_do 기준으로 어느 단계가 맞는지 정합니다. 이 단계가 낮은 쪽일 때만 판정합니다("유지" 또는 "삭제: <단계>단계가 맞음"). 높은 쪽이면 "상위 단계: 낮은 단계의 검토를 따름"이라고만 적습니다.
   ```
   낮은 단계의 검토가 "유지"면 높은 단계의 항목을 지우고, "삭제"면 낮은 단계의 항목을 지운다. 그 밖의 검토 결과는 "절차" 4번과 같이 반영하고(수정·삭제), 바뀐 항목이 있으면 3번 검사를 다시 한 뒤 **바뀐 항목만** 그 단계의 검토 에이전트에게 한 번 더 보낸다. 세 번째 검토는 하지 않는다.

5. **검토표를 만들고 멈춘다**
   ```bash
   $DM review-sheet
   ```
   출력의 `reviews`에 단계마다 `review_1.md`…`review_5.md`가 있고 `review`(`review.md`)는 차례와 단계 사이 겹침만 담는다. 단계마다 한 줄씩(항목 수, 주제·용어, 분야, 검사 오류·경고, 검토에서 고친·지운 수)과 열어 보지 못한 자료를 보고한다. 마지막 줄: "단계별 검토표를 보고 승인하시면 `/dic-maker apply`로 다섯 단계를 한 번에 사전에 넣습니다. 빼고 싶은 항목은 단계와 id를 말씀해 주시거나 초안 파일에서 지우세요." **여기서 끝낸다. apply를 스스로 실행하지 않는다.**

**이어 하기 (`c`)**: `$DM status`의 `run.mode`가 `all`이면 `missing_files`로 단계마다 아직 없는 분야 파일을 본다. 비어 있지 않은 단계만 2번의 에이전트를 다시 띄우고(있는 파일은 읽고 이어 쓴다), 모두 있으면 3번부터 한다. `writing`에 파일이 있으면 다른 세션의 에이전트가 아직 쓰는 중일 수 있으니 1분 기다렸다가 다시 본다.

## 캠페인 (auto)

`/dic-maker <단계> <개수> auto`로만 연다. 60개 회차를 이어 돌리며 **회차마다 사람 승인 없이** 검토·적용·커밋한다. 사람이 하던 승인을 검토 에이전트의 판정 파일(`review-verdicts.json`)과 스크립트의 자동 문이 대신하므로, 의심스러운 항목은 넣지 않고 뺀다. 한 회차는 "절차"와 같은 흐름이고(분야 5개 × 조사 에이전트 5개), 60을 한 번에 늘리지 않는 이유는 에이전트 하나가 공식 문서를 읽으며 쓸 수 있는 양이 12개쯤이기 때문이다. 토큰이 끊겨도 이미 커밋된 회차는 남고, `c`로 이어 한다.

1. **캠페인 열기** (1회차 계획까지 한 번에 한다)
   ```bash
   $DM campaign --level <단계> --total <개수>
   ```
   `--total`은 최대 1000이다. 그 단계가 이미 목표치(`gaps`의 `topic_target`·`term_target`)에 닿았으면 열리지 않는다. 사용자가 넘기자고 분명히 말했을 때만 `--over-target`을 붙인다. 진행 중인 실행이나 캠페인이 있으면 멈추고 `/dic-maker c`나 `/dic-maker s`를 안내한다.
   출력은 "절차" 1번의 `start`와 같고 `round`·`auto`·`campaign`(`total`·`done`·`remaining`·`rounds_planned`)이 더 있다. 한 줄로 알린다: "📚 dic-maker · 캠페인 <level>단계 <total>개 · 회차 <round>/<rounds_planned> (<count>개) · 자동 적용 · 취소 ESC 후 /dic-maker s". 기다리지 않고 진행한다.

2. **조사·검사·검토**는 "절차" 2~4번을 그대로 한다. 검토 에이전트 지시문에는 아래 두 줄을 덧붙인다.
   ```
   - 판정 파일: <저장소>/.dic-maker/review-verdicts.json 에 JSON 객체 하나를 씁니다. 키는 항목 id, 값은 {"verdict": "keep" | "fix" | "drop", "verified": true | false, "note": "<한 줄>"}입니다. verified는 refs를 WebFetch로 실제로 열어 summary·objectives를 대조했을 때만 true입니다. 열지 못했으면 false로 쓰고 note에 이유를 적습니다. 초안의 모든 항목에 판정을 씁니다. 빠진 항목은 사전에 들어가지 않습니다.
   - 이 캠페인은 사람 승인 없이 판정대로 넣습니다. 확신이 없으면 keep 대신 fix나 drop으로 씁니다.
   ```
   "수정"을 반영한 뒤 바뀐 항목만 같은 검토 에이전트에게 한 번 더 보낼 때, 판정 파일의 그 항목도 다시 쓰게 한다(해결됐으면 `keep`). 두 번째 검토 뒤에도 `fix`로 남은 항목은 자동 문이 뺀다. 세 번째 검토는 하지 않는다.

3. **검토표를 남기고 자동 적용한다**
   ```bash
   $DM review-sheet
   $DM apply --auto --note "dic-maker 캠페인 <회차>회차로 <단계>단계에 주제 n개, 용어 m개를 더했다"
   ```
   자동 문은 이렇게 거른다. 판정이 `keep`이고 `verified`가 true인 항목만 남긴다. 판정이 없거나 `drop`·`fix`이거나 자료를 확인하지 못한 항목, 그리고 그런 항목에 딸린 용어·선수 관계의 항목은 뺀다. 남은 항목에 검사 오류가 있으면 오류에 이름이 든 항목을 빼고 다시 검사한다(최대 3번). 뺀 항목은 `.dic-maker/campaign-dropped.json`에 근거와 이유가 남고, 검토표·검토 결과·판정 파일은 `.dic-maker/campaign/round_<회차>_*`로 옮겨진다. 남는 항목이 없으면 사전과 버전은 그대로이고 회차는 0개로 기록된다.
   출력의 `dropped`(뺀 항목과 이유)와 `campaign.next`(`continue`·`stop`)를 본다.

4. **테스트와 커밋**은 "적용 (apply)"과 같다. 테스트가 실패하면 커밋하지 않고 캠페인을 멈추며 결과를 그대로 알린다. 푸시와 플러그인 버전 올리기는 회차마다 하지 않고 캠페인이 끝났을 때 한 번 묻는다.
   ```bash
   python3 -I -m unittest discover -s tests
   git add catalog skills/study-notes/catalog.json
   git commit -m "feat(catalog): <note> (사전 <새 버전>)"
   ```
   회차를 한 줄로 알린다: "✅ <회차>회차 · 사전 <새 버전> · 넣음 n개 · 뺌 k개 (<이유별 수>) · 누적 <done>/<total>".

5. **다음 회차**: `campaign.next`가 `continue`면
   ```bash
   $DM start
   ```
   로 다음 회차를 열고(단계와 개수는 캠페인이 정한다) 2번부터 되풀이한다. 사용자에게 묻지 않는다. 출력에 `campaign_finished`가 있으면 캠페인이 닫힌 것이다. `stop`이거나 `campaign_finished`면 6번으로 간다. 멈추는 조건은 세 가지다: 목표 수 도달, 단계 목표치 도달(`--over-target`이 아니면), 두 회차 연속 산출이 몫의 절반 미만(좋은 항목이 고갈된 신호).

6. **보고**: `$DM status`의 `campaign`을 보고 회차별 한 줄(버전, 넣은 수, 뺀 수), 누적 수와 멈춘 이유(`stop_reason`), 뺀 항목 중 다시 볼 만한 것(`campaign-dropped.json`에서 "확인하지 못했다"·"판정이 없다"인 것)을 알린다. 검토표가 `.dic-maker/campaign/`에 있다고 알린다. 그다음 **푸시할지 묻고**, study-notes 플러그인 사용자는 플러그인 버전을 올려 배포해야 새 사전을 받는다고 한 줄 덧붙인다.

**이어 하기 (`c`)**: `$DM status`의 `campaign.status`가 `running`이면 캠페인이다. `run`이 있으면 그 회차를 잇는다(초안이 있으면 "절차" 3번부터, 판정 파일이 있으면 3번의 자동 적용부터). `run`이 없으면 `$DM start`로 다음 회차를 연다. `campaign.status`가 `finished`·`cancelled`면 캠페인이 아니라 보통 실행의 이어 하기다.

**취소 (`s`)**: `$DM cancel`이 진행 중인 회차의 초안을 버리고 캠페인을 닫는다. 이미 커밋된 회차는 사전에 남는다. 출력의 `message`를 그대로 전한다.

## 적용 (apply)

사용자가 `/dic-maker apply`를 불렀을 때만 실행한다. 캠페인(auto)에서는 회차마다 `apply --auto`를 스스로 실행하지만, 그 밖에는 사람이 승인하기 전에 apply를 스스로 실행하지 않는다. `all` 실행도 같은 명령으로 다섯 단계를 한 번에 넣는다. 사용자가 뺄 항목을 말했으면 먼저 초안 파일에서 지운다.
```bash
$DM apply --note "<이번 추가를 한 줄로>"
```
검사 오류가 있으면 적용되지 않는다. 오류를 고치거나 그 항목을 빼고 다시 실행한다. 통과하면 `catalog/items`에 들어가고 `VERSION`이 올라가며 `CHANGELOG.md`에 한 줄이 생기고 `build`로 `dist/`와 `skills/study-notes/catalog.json`이 갱신된다. 그다음:
```bash
python3 -I -m unittest discover -s tests
git add catalog skills/study-notes/catalog.json
git commit -m "feat(catalog): <note> (사전 <새 버전>)"
```
테스트가 실패하면 커밋하지 않고 결과를 그대로 알린다. **푸시는 사용자에게 묻는다.** 보고에는 새 버전, 주제·용어 수, 분야별 수, 후보함에서 반영된 개념(`box_covered`)을 적는다. study-notes 플러그인으로 쓰는 사람은 플러그인 버전을 올려 배포해야 새 사전을 받는다는 것을 한 줄 덧붙인다.

## 갱신 (refresh)

```bash
$DM refresh --links
```
`stale_volatile`(확인한 지 90일 넘은 빨리 바뀌는 항목)과 `broken_links`를 받는다. 항목 5개씩 에이전트 하나에게 맡겨 자료를 다시 열어 대조하게 한다. 내용이 바뀌었으면 `catalog/items`의 그 항목을 고치고(이 모드에서만 사전 파일을 직접 고친다), 확인이 끝난 id는 `$DM mark-checked --ids <id> ...`로 날짜를 바꾼다. 죽은 링크는 같은 기관의 살아 있는 페이지로 바꾸고 `$DM check`가 아니라 `python3 -I catalog/tools/catalog.py check`와 `links`로 확인한다. 끝나면 `build`와 테스트, 커밋까지 "적용"과 같다.

## 상태 (d)·취소 (s)

```bash
$DM status
$DM cancel
```
`status`는 사전 버전과 항목 수, 단계별 현황(`levels`의 주제·용어와 목표), 진행 중인 실행과 분야별 초안 수(`all`이면 단계별), 검토표 경로(`reviews`), 캠페인(`campaign`의 단계·목표·누적·회차 기록·상태)을 표로 보여 준다. `cancel`은 초안(단계 폴더 포함)·실행 기록·검토표·판정 파일을 지우고 캠페인을 닫으며 사전은 건드리지 않는다.

## 품질 규칙 (요약)

자세한 규칙은 `$DM guide`에 있다. 메인이 지킬 것만 적는다.
- 자료가 먼저다. 자료 없는 항목, 블로그·강의·roadmap.sh에서 온 항목은 받지 않는다.
- 주제와 용어는 그 단계의 목표 비율로 함께 늘린다. 억지로 개수를 채우지 않는다.
- 별칭은 실제 대화 기록으로 오탐률을 잰다(`check`가 한다). 이 기록은 이 컴퓨터에만 있고 초안이나 사전에 들어가지 않는다.
- 사람이 승인하기 전에는 사전 파일을 바꾸지 않는다. `refresh`와 사용자가 `auto`로 연 캠페인만 예외다. 캠페인에서는 검토 에이전트의 판정 파일과 자동 문이 승인을 대신하고, 의심스러운 항목은 넣지 않는다.
- 기존 항목을 고치자는 제안은 보고에 적고, 이 실행에서 고치지 않는다.

## 문제가 생기면

- `사전 저장소가 아닙니다`: `claude-study-notes`를 받은 폴더에서 다시 부른다. `git clone https://github.com/thinqsimon/claude-study-notes`.
- `진행 중인 실행이 있습니다`: `/dic-maker c`로 잇거나 `/dic-maker s`로 버린다.
- `검사 오류가 있어 적용하지 않습니다`: `check` 출력의 오류를 고치거나 그 항목을 초안에서 뺀다.
- `적용 뒤 검사에 실패했습니다`: `git checkout catalog/items catalog/VERSION catalog/CHANGELOG.md`로 되돌리고 초안을 다시 검사한다.
- 대화 기록이 없어 별칭 오탐률을 못 잰다는 메모(`alias_sessions: 0`)는 오류가 아니다. 넓은 말 목록과 겹침 검사만으로 진행한다.
- `L3/fe.json: JSON 항목 목록이 아닙니다`처럼 자기 단계 파일이 깨졌다는 오류는 그 파일을 고친다. 다른 단계 파일이면 `check --level`은 "쓰는 중"으로 건너뛰고, 전체 검사는 에이전트가 모두 끝난 뒤에만 돌린다.
- `[단계 간]` 오류가 apply를 막으면 두 단계 중 한쪽 초안에서 그 항목을 지운다. 어느 쪽인지는 `review-findings_<낮은 단계>.md`의 판정을 따른다.
- `review-verdicts.json이 없거나 객체가 아닙니다`: 캠페인의 검토 에이전트가 판정 파일을 쓰지 않았다. 검토를 다시 띄워 판정 파일을 쓰게 한 뒤 `apply --auto`를 다시 한다. 판정 없이 넣지 않는다.
- `캠페인은 N단계입니다`·`캠페인이 진행 중이라 --all, --box를 쓸 수 없습니다`: 캠페인을 끝내거나 `/dic-maker s`로 닫은 뒤 한다.
- `캠페인을 열 수 없습니다: … 목표치에 도달했다`: 그 단계는 목표치가 찼다. 사용자가 넘기자고 하면 `--over-target`으로 다시 연다.
- 캠페인에서 뺀 항목은 `.dic-maker/campaign-dropped.json`에 있다. 자료 미확인으로 빠진 것은 사람이 보고 `box`나 보통 실행으로 다시 넣을 수 있다.
- 작업 폴더는 저장소의 `.dic-maker/`이고 git이 무시한다. 지난 적용 기록은 `.dic-maker/history/`에, 캠페인 회차별 검토표는 `.dic-maker/campaign/`에 남는다. `.dic-maker/lock`은 잠금용 빈 파일이라 지워도 된다.
